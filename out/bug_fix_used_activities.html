Replan loop: stale results poisoning Day 2 candidates

Bug in ItineraryExecutorNode._run_build_day — Paris 4-day trip hit max replans and fell back to the degraded plan.

Bug src/agent/nodes/itinerary/executor.py

Observed failure

Running the planner for a 4-day Paris trip, all 10 steps succeeded on the first pass. The LLM quality reviewer rejected the plan because Day 4 had fewer than 2 activities. That triggered a replan — and from there it spiraled into the fallback path: 

REPLAN attempt 1/3 — reason: Day 4 has fewer than 2 activities
  Step 1/5: build_day_schedule (Day 1) ok
  Step 2/5: build_day_schedule (Day 2) FAILED — no activity candidates after deduplication.

REPLAN attempt 2/3 — reason: Day 2: no activity candidates after deduplication
  Step 1/5: build_day_schedule (Day 1) ok
  Step 2/5: build_day_schedule (Day 2) FAILED — same error

OBSERVER -> FALLBACK (max retries=3 reached)

Root cause

The dedup check _used_activities(results) walked every entry in the results dict — including stale slots from abandoned plan runs.

How step keys diverge across replans

Each result is stored at step_key = f"{step.step_type}_{step.step_id}". The planner renumbers step_id sequentially on every replan, so the same Day 2 build ends up at different keys across runs:

Plan runBuild-day keys in results
First pass (10 steps)build_day_schedule_6 .. _9
Replan #1 (5 steps)build_day_schedule_1 .. _4  + stale 6..9 still present

Why Day 2 specifically died

  1. The fetch_activities result is cached, so the activity selection assigned to Day 2 is identical across runs (say, 5 names).
  2. ActivitySelector enforces no repeats across days — those 5 names appear only in Day 2’s selection.
  3. On the first pass, ScheduleEngine fit all 5 of them into stale Day 2’s slots.
  4. On replan, _used_activities(results) aggregated activity names from every result — stale Days 1–4 plus the new Day 1 — and reported all 5 as “used.”
  5. Day 2’s selection filtered against that set was empty ⇒ no activity candidates after deduplication.

Why Day 1 didn’t fail the same way

The selector hands each day 4–6 candidates; ScheduleEngine fits a subset (time / operating-day constraints). Day 1’s selection had leftovers that were not in any stale slot, so after dedup it still had candidates. Day 2’s selection happened to be fully scheduled on the first pass, leaving nothing.

Bug summary. The dedup pool grew monotonically across plan runs — each replan inherited every previously-scheduled activity name. With no-repeats enforced and selection cached, the second attempt was guaranteed to starve on whichever day was fully fit the first time.

The fix

Fix Scope _used_activities to result keys that belong to the current plan run. Anything stored under a step key from an abandoned earlier plan is ignored.

Changes (executor.py)

1. Build the current plan’s key set at dispatch time.

elif step.step_type == "build_day_schedule":
    current_plan_keys = {f"{s.step_type}_{s.step_id}" for s in plan.steps}
    result = self._run_build_day(step, results, destination, trip_days,
                                 current_plan_keys)

2. Pass it down into _run_build_day.

def _run_build_day(
    self, step, results: dict, destination: str, trip_days: int,
    current_plan_keys: set[str],
) -> dict:
    ...
    day_names  = selection.get(f"day_{day_num}", [])
    used       = _used_activities(results, current_plan_keys)
    day_names  = [n for n in day_names if n not in used]

3. Filter results inside the helper.

def _used_activities(results: dict, current_plan_keys: set[str]) -> set:
    used: set[str] = set()
    for key, wrapped in results.items():
        if key not in current_plan_keys:
            continue
        day_data = _inner_data(wrapped)
        if not isinstance(day_data, dict):
            continue
        for slot in day_data.get("slots", []):
            if slot.get("slot_type") == "activity" and slot.get("name"):
                used.add(slot["name"])
    return used

Correctness check: cross-day dedup still works

Within a single plan run, Day 1 commits its result before Day 2 starts, and Day 1’s key is in current_plan_keys. So Day 2 still sees Day 1’s scheduled activities and excludes them.

Belt-and-suspenders: the LLM activity selector already enforces no-repeats at selection time (activity_selector.py:56), so the used filter is a redundant safety net. Both layers remain intact.

What changed. Only slots from abandoned prior plan runs are skipped. Slots produced during the active plan still count toward dedup as before.

Out of scope (related)

The original trigger — Day 4 having fewer than 2 activities — is upstream of this fix. It can stem from:

  • The LLM selector under-allocating Day 4 (top-rated names front-loaded into earlier days).
  • ScheduleEngine rejecting Day 4 candidates on opening hours / operating_days for the actual calendar date.
  • Genuinely thin pool after preference filters (kosher, vegan, etc.).

If it keeps tripping after the dedup fix, instrument the selector and ScheduleEngine to log per-day counts and reject reasons.
