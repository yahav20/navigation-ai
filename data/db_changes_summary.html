Why We Migrated to SQLite
🗄️

Real Relational DB

JSON is a flat file — no queries, no indexes, no relations. SQLite gives us proper SQL so the agent can filter, sort and join data exactly like a production system.

🌍

City + Country Schema

The new flights table stores both city and country for origin and destination, enabling a two-step search: look for a city first, fall back to the country if no direct match is found.

⚡

Indexed Lookups

Case-insensitive indexes on destination_city and destination_country make every tool call fast regardless of how many rows are in the DB.

🔌

Provider Pattern

The BaseDataProvider interface means the agent never knows whether it's talking to JSON or SQLite. Swap providers by changing one line in the factory.

📦

Self-Contained

SQLite ships with Python's stdlib — no server, no Docker, no credentials needed. Any teammate can clone the repo and run python data/init_db.py to be up instantly.

🚀

Ready for Session 4

LangGraph's SqliteSaver for persistent memory will use the same SQLite file, so adding checkpointing in the next session requires zero infrastructure changes.

Country Fallback — Flight Search Logic

How fetch_flights handles a city with no direct flights

User asks for flights
to "Lyon"
→
Search by
destination_city
→
No results
→
Look up country
for "Lyon" = France
→
Return all flights
to France (e.g. Paris)

The agent receives a clear message: "No direct flights to Lyon, but here are flights to other cities in France." This gives the LLM context to suggest alternatives without looping.
